## G2. A restore in a spyc that runs tabs without jars starts a second copy of a program whose jar still runs

**Verdict:** `confirmed`, severity high kept. Two corrections to the text, neither of which weakens it: there are more ways in than it lists, and one clause of the consequence needs saying more exactly.

**Evidence (lines read):**

- `src/app/pane_starts.rs:118-145`, `launch_tab_pane`, read whole. Its first statement is `if !(jars && jar::honoured()) || self.runtime.jarless.chosen { return Pane::launch(launch, wake); }` (:126-127). `restoring` is used only after that, in `Taking::Start(restoring.cloned()…)` (:143). The `launch` that `spawn_pane_tab` builds always has `jar: None` (`src/app/pane_tabs.rs:348-357`), and `PtyHost::spawn` with `spec.jar` `None` goes to `spawn_native` (`src/pane/pty_host.rs:243-253`). So with jars off, a restored tab's saved `jar_socket` is never read and the program starts on spyc's own PTY.
- The only liveness check of a restored tab's socket that happens before a launch without a jar is `start_without_jar` (`src/app/jarless.rs:137-144`). It runs only for the `Waiting` entries of a tab that already failed with `NoUsableJar`, either at the offer's `y` or through `tab_has_no_usable_jar` once the offer has been taken. A restore that comes after `chosen` is set never gets there, because `launch_tab_pane` returns before any jar is asked for. The module's own doc (`jarless.rs:10-11`) and its test (`a_tab_whose_jar_may_still_run_is_not_started_without_one`) show the authors meant to protect this case, and the guard covers only one way in.
- Nothing on the restore side stops it. `restore_plans` (`src/app/session_restore.rs:757-789`) clears `jar_socket` only for fresh copies (`fresh_tab`, :804-813). `Held::by_running` (`src/state/sessions/manifest.rs:255-267`) counts only tabs of manifests whose spyc is running, and after a crash, a `^d` or an `:upgrade` no spyc is running (`save_released` sets `pid = None`, `src/app/detach.rs:227-234`). So the plan resumes, and `restore_tab` arms the claude `/resume <sid>` keystrokes whenever `!entry.pane.adopted() && !entry.pane.detached()` (`session_restore.rs:465-480`), which a native pane always is. `rg -n jar_socket src/app src/lib.rs src/state/sessions` finds no other reader on the restore path.
- The jars of a crashed spyc do run on: `src/app/orphan_jars.rs:1-8` and `ARCHITECTURE.md:1102-1112` describe live jars with no owner after a crash, by design.
- No test covers it. The restore test in `src/app/harness_tests/jar_start.rs:339-381` runs with jars on. `rg 'jars = false'` over `src` and `tests` finds only the config tests and the jarless flash text.
- It goes against the tree's own invariant: `ARCHITECTURE.md:1071-1072` ("A restored tab whose jar may still run is never started that way") and `:1121` ("A tab's program never runs twice"). The owner's decision 6 (`docs/drafts/JAR_PRODUCTION_PLAN.md:459-467`) makes `jars = false` "spyc without jars". It does not make running a program twice acceptable, so the code is wrong here, not the documents.

**Correction 1: more ways in than the finding lists.** Both of these restore a session whose jars still run, in a build where `honoured()` is false, with no crash at all:

- `:upgrade` from an rc build into an installed `3.0.0` binary. `upgrade_in_place` saves the session as released, leaves the jars running and `exec`s the installed spyc (`detach.rs:208-222`). The new image then restores the session through `restore_own_session` → `restore_session` (`detach.rs:340-353`).
- `spyc attach` for a session that an rc build handed over with `^d`. `hand_over` starts the session jar on the installed spyc's path with `Begin::OnAttach` (`detach.rs:183-192`), so the program that restores the session on attach is whatever binary is installed at that moment.

This makes V1's consequence wider than G2 says. The finding's "`^d`" clause holds through `spyc attach` as well as `spyc -r`.

**Correction 2: the orphan path is narrow.** The orphan pop-up's `r` with `chosen` set does reach `spawn_pane_tab(…, Some(&saved), …)` (`orphan_jars.rs:196-212`) and launches natively, and the orphan's jar is `Live` by construction. For that to happen, though, the first `NoUsableJar` of the session has to land after the look has started. A failure during startup sets `chosen` before the look, and `jars_wanted` (:63-67) then turns the look off. Jars start from spyc's store copy (`ARCHITECTURE.md:1131-1135`), which makes a failure mid-session rare. The same goes for `:attach project` or `:attach tab` after the offer was taken. These paths are real, but they are the rare ones.

**Why high still holds without V1.** Suppose V1 is fixed as the plan's decision 1 requires. `[pane] jars = false` is still "the way back" (`JAR_PRODUCTION_PLAN.md:262-263`), and the moment a user is most likely to flip it is right after jars have misbehaved: a crash or a kill, with the jars still running. The next `spyc -r` then starts every jarred program a second time, and a claude tab gets `/resume <sid>` typed into the conversation its jarred twin is still working in. That breaks the stated invariant silently, and it is reachable by an ordinary user action.

**What would have to be true for me to be wrong:** something outside `launch_tab_pane` turns jars off only when no saved session holds a live `jar_socket`, or a config reload or startup step refuses `-r`, `:attach` and the own-session restore while jars are off. I found no such check (`rg jar_socket`, `rg 'honoured\(\)'`). Or the Claude Code conversation store rejects a second process resuming a live session, which would turn the claude case into a refused resume rather than two writers. The duplicate program would still run, though.
