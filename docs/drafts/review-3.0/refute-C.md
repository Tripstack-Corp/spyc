## C2. A jar silent for about 40 s leaves its tab `[detached]` for the session, and `^a R` then runs the program twice

**Verdict:** `partly`. Every step of the mechanism holds as written. The trigger is narrower than "starved ... under load", and the double run is broader than the trigger: it doesn't need the clock at all. Narrower form, in two parts:

1. **The lost retake (medium).** A jar this spyc owns whose process does not run for more than `WRITE_STALL` (20 s) while spyc has more queued for it than the two socket buffers hold, and then for most of `ADOPT_WAIT` (20 s) more, leaves its tab `[detached]` for the session, and nothing takes it back when the jar runs again. That goes against decision G ("a spyc that loses its lease takes it back when the jar is free"). But "starved under load" does not get you there. The jar reads its owner on a thread of its own that never waits on the program or on a write: input goes to an inbox fed to the PTY by another thread, and replies go to an outbox. So the jar stops reading only when the whole process is stopped (`SIGSTOP`, a debugger), swapped out for tens of seconds, or parked for an upgrade, which the jar bounds at 15 s (`PARKED_AT_MOST`), under both 20 s waits.
2. **The double run on `^a R` (high, kept).** `^a R` on **any** `[detached]` tab starts a second copy of its program in a new jar, with no question, while the old jar's program runs on. That includes the `[detached]` that decision G intends (another spyc owns the jar) and the one for a missing token, so it is reachable without any clock running out.

**Evidence (lines read; the reviewer's probe logs read):**

- The lapse. `src/pane/jar/mod.rs:704-711` (`connect`): every owner connection is `split_queued(PING_EVERY, WRITE_STALL)`. `crates/spyc-jar/src/client.rs:181-194`: `set_write_timeout(Some(stall))` on the socket. `:263-290` (`write_queued`): a write that fails or times out ends the loop and shuts the socket. `src/pane/jar/link.rs:227-234` (`read_frames`): the reader's error, with the jar's lock still held (`socket_state` → `Live`, `place.rs:227-238`, which a stopped process still holds), sets the exit to `Lost::Held`, labelled `detached` (`:259-265`).
- One retake. `src/pane/mod.rs:357-366` (`lease_lapsed`) needs `host.jarred()`, which is `self.jar.is_some()` (`src/pane/pty_host.rs:637-639`). `src/app/pane_starts.rs:149-200` (`retake_lapsed_tabs`, called from `pre_recv.rs:209`) swaps in a stand-in and takes the jar back on a worker (`Taking::Retake` → `Spec::retaking`, `mod.rs:208-214`). In `spawn` (`mod.rs:428-443`) a live socket goes to `adopt` (`:544-555`), whose `Client::connect(..., ADOPT_WAIT, ...)` failing gives `link::detached`, an `Ok` stand-in. That stand-in has `signals: None` (`link.rs:445-481`), so `set_jar` leaves `jar` `None` (`pty_host.rs:282-288`), so `jarred()` is false, `detached()` is true (`:323-325`) and `lease_lapsed` is false for good. `rg -n "retake_lapsed_tabs|lease_lapsed"` finds no other caller; `rg -i "retake|take.{0,10}back"` in `src/app` finds no other path that takes a live tab's jar back during a session (the orphan look in `orphan_jars.rs` runs at start). The existing test `a_detached_tab_is_not_taken_back` (`src/app/harness_tests/jar_start.rs:448`) pins the behaviour.
- The reviewer's macOS log `scratchpad/unit-c/pasteR1/events.log` agrees with that timing: stopped at 7.6 s, first `detached` 40.1 s later (20 s stall, then the 20 s adopt wait), no change after `SIGCONT`, typing never reaches the program. Linux `linux/pasteR120` the same at 46.5 s. The control `linux/pasteR` (continued while the retake still waited) was taken back and `^a R` asked first, as the code predicts.
- Why load alone doesn't trigger it. `crates/spyc-jar/src/jar/conn.rs:99-179` (`run_conn`): one thread reads the owner; another (`stream_log`) writes. `:268-278`: `Input` only calls `queue_input`. `crates/spyc-jar/src/jar/input.rs:1-9`, `:39-49`, `:73-111`: the inbox is fed to the PTY by `feed_pty` on its own thread ("the owner's connection goes on being heard"). `crates/spyc-jar/src/jar/outbox.rs:30-47`: a reply is queued, never written by the reader (SPYC-TRAP `jar-one-writer`). `docs/drafts/JAR_PROTOCOL.md:956-978`: 20 s outwaits the jar's longest documented silence, 15 s. A busy machine slows the jar; it doesn't leave its reader unscheduled for 20 s.
- The double run. `src/app/pane_tabs.rs:34-36` (`needs_live_child_confirm`) asks only for a tab neither closed nor reaped. A detached stand-in is both: `GoneChild(Some(Held))` answers `try_wait` at once (`link.rs:560-563`), and its note reader ends at once since `held` is `None` when `ended` is set (`:470`). `restart_tab_now` (`pane_tabs.rs:796-842`) calls `try_kill`, which on `GoneChild` does nothing (`link.rs:551-554`), then `open_pane_tab_into` → `spawn_pane_tab` with `restoring: None`, so `TabInfo::new` gives a fresh uuid id (`src/pane/tabs.rs:452-458`), so `spawn` (`mod.rs:447`) names a new socket, which `ended_within` finds `Missing`, and a new jar starts. Nothing reads the old tab's `jar_socket` on that path. The same holds for the stand-in `adopt` returns when the jar refuses this spyc (another owner, `mod.rs:552-555`) or when no token exists (`:549-551`). The reviewer's log shows it: `restarted sh -c …` with no `[y/N]`, then two `spyc-jar sh` processes and the old program alive.
- One correction to the "other road" bullet. When `adopt` fails after a welcome (`client.recv(ADOPT_WAIT)?` at `mod.rs:570`, or `connect(...)?` at `:596`), `land_pane_start` labels a **retake** `Lost::Gone` ("jar lost"), not `[not started]` (`pane_starts.rs:318-322`). Only a restore gets `[not started]`. The retake case is worse than the finding says: the tab claims the jar is gone while it and its program run on, and `^a R` (no question, the tab is closed) starts a second copy.

**What would have to be true for me to be wrong:** on part 1, that something ordinary stops a jar's owner reader for 20 s with the process running (for example a lock in the jar held across a blocking call, which is Unit B's question); then "under load" holds and part 1 is high too. On part 2, that `^a R` on a `[detached]` tab is meant to start a fresh copy beside the old one, which neither decision G nor the plan says.

## C1. A restored tab whose jar still runs is started a second time when jars are off

**Verdict:** `confirmed`. Only checked as asked: does the red test fail, and for the stated reason? It does, and I watched it do so with both programs alive at once. Severity high kept, as in `refute-G.md` for G2.

**Evidence (failing test, run by me):** `review_c_a_restored_tab_whose_jar_runs_is_not_started_again_with_jars_off` (`~/src/spyc.worktrees/review/3.0-c/src/app/harness_tests/jar_start.rs`, uncommitted diff read whole). Run twice from the built test binary with scratch `HOME`, `XDG_*` and `TMPDIR`, `SPYC_*` unset:

```
assertion `left == right` failed: its program ran twice: 3136
3189
  left: 2
 right: 1
test result: FAILED. 0 passed; 1 failed; ... finished in 3.22s
```

On the second run I sampled `ps` 1.6 s in, during the test's 3 s sleep: pid file `3723, 3777`; `3723 3722 cat`, whose parent `3722` is `spyc-jar sh --wire 1`; `3777 3615 cat`, a child of the test process itself, that is, on spyc's own PTY. So the second start ran natively while the first program still ran in its jar.

Why it fails for the stated reason, not some other one:

- The first program survives the "crash". `sever_jar` → `Signals::sever` → `out.close()` (`src/pane/jar/mod.rs:347-349`) queues `Close`. The `Kill` that `PtyHost::drop` sends next (`src/pane/pty_host.rs:721-734`, through the jar only, `:591-598`, never by pid) is queued behind it and never written, since `write_queued` stops at `Close` (`crates/spyc-jar/src/client.rs:281`). The test checks the socket is still `Live` before restoring, and the `ps` sample confirms it.
- The second start comes from the jars-off branch. `spawn_pane_tab` reads `config.pane.jars` (`src/app/pane_tabs.rs:344`), which the test set to `false`, and passes `restoring = Some(&saved)` with the saved `jar_socket` to `launch_tab_pane`, whose first statement `if !(jars && jar::honoured()) || self.runtime.jarless.chosen { return Pane::launch(launch, wake); }` (`src/app/pane_starts.rs:126-127`) never looks at `restoring`. `Launch.jar` is `None` (`pane_tabs.rs:357`), so `PtyHost::spawn` goes to `spawn_native` (`pty_host.rs:243-253`). The test calls `spawn_pane_tab` directly, as `open_restored_pane_tab` does (`src/app/session_restore.rs:18-30`).
- Nothing else in the test could append a second pid: a jar never restarts its program (`JAR_PROTOCOL.md` R5), and the test opens no other tab.

**What would have to be true for me to be wrong:** that a real restore never reaches `spawn_pane_tab` with a live saved `jar_socket` while jars are off (some earlier step clearing `jar_socket` or refusing the restore); `refute-G.md` looked for one and found none, and I found none on the path above.
